\# SIH26054 – AI‑Enabled Real‑Time Digital Twin for Aero‑Piston Engines (MALE UAV)\\n\\n## 1. Background\\nMedium Altitude Long Endurance (MALE) UAVs are increasingly being deployed for long‑duration intelligence, surveillance, reconnaissance (ISR) missions. Reliability and availability of propulsion systems are critical because piston‑engine failures during flight may lead to mission abort, asset loss, or unsafe recovery conditions.\\n\\nConventional engine monitoring systems used in UAVs are primarily threshold‑based and reactive. They indicate failures only after an abnormality has already occurred and have limited capability to estimate Remaining Useful Life (RUL), predict degradation trends, or simulate mission‑wise engine behaviour under varying environmental and operating conditions.\\n\\nA Digital Twin (DT) framework for aero piston engines can significantly improve predictive maintenance, operational reliability, mission planning, and life‑cycle management by creating a continuously synchronized virtual representation of the physical engine using real‑time sensor data, physics‑based models and AI/ML techniques.\\n\\n## 2. Problem Statement\\nCurrent UAV ground‑control health‑monitoring solutions are reactive, lack predictive insight, and cannot provide realistic mission‑level simulations. The challenge is to develop an indigenous, modular Digital Twin system that delivers real‑time state estimation, anomaly detection, fault prediction, degradation tracking, RUL estimation, and mission replay for aero‑piston engines on MALE UAVs.\\n\\n## 3. Objectives\\n- Build a real‑time digital replica of an aero‑piston engine that ingests live (or synthetic) telemetry.\\n- Provide continuous health‑index calculation and visualisation.\\n- Detect anomalies and predict probable faults before they manifest.\\n- Estimate degradation trends and Remaining Useful Life (RUL).\\n- Enable mission‑profile simulation and post‑flight replay.\\n- Deliver a web‑based dashboard for operators, propulsion engineers, maintenance engineers and fleet managers.\\n\\n## 4. Scope\\n### In‑Scope\\n- Telemetry ingestion via simulated CAN/SocketCAN (synthetic data for the hackathon).\\n- Physics‑informed engine model (RPM, CHT, EGT, oil pressure/temperature, fuel flow, vibration, battery/alternator health, injection timing).\\n- AI/ML layers: anomaly detection, fault classification, degradation regression, RUL estimation.\\n- WebSocket‑based real‑time data streaming to a React dashboard.\\n- Mission‑profile definitions (standard ISR, high‑altitude, hot‑weather, aggressive).\\n- Fault‑injection module (misfire, injector degradation, lubrication issue, sensor drift, overheating, abnormal vibration, battery/alternator degradation).\\n- Post‑flight replay and report generation.\\n### Out‑of‑Scope\\n- Direct integration with real aircraft CAN bus hardware.\\n- Flight‑certification or regulatory compliance.\\n- Large‑scale fleet management (focus on a single‑engine demo).\\n- Edge‑device deployment (backend runs locally for the demo).\\n\\n## 5. Functional Requirements\\n1. Telemetry Acquisition\\n - FR‑1.1: Accept telemetry packets (JSON/CSV) containing the sensor list.\\n - FR‑1.2: Store raw telemetry in SQLite with timestamps.\\n2. Engine Simulation\\n - FR‑2.1: Generate synthetic healthy telemetry following defined mission profiles.\\n - FR‑2.2: Apply fault‑injection curves based on severity and duration.\\n3. Digital Twin Core\\n - FR‑3.1: Compute expected sensor values using simplified physics equations.\\n - FR‑3.2: Calculate residuals (observed – expected).\\n - FR‑3.3: Derive a normalized Health Index (0‑100).\\n4. AI/ML Layer\\n - FR‑4.1: Anomaly detection (Isolation Forest) producing a score 0‑1.\\n - FR‑4.2: Fault classification (multiclass RandomForest) returning probabilities for each fault type.\\n - FR‑4.3: Degradation regression (Gradient Boosting) outputting a degradation level 0‑1.\\n - FR‑4.4: RUL estimator (Regression) providing hours remaining and confidence level.\\n5. WebSocket Broadcast\\n - FR‑5.1: Stream telemetry, twin state, and ML predictions to connected clients.\\n - FR‑5.2: Throttle messages to max 5 per second per client.\\n6. Dashboard UI\\n - FR‑6.1: Real‑time plots for key sensors (RPM, CHT, EGT, oil pressure, vibration).\\n - FR‑6.2: Health‑Index gauge and anomaly/fault alerts.\\n - FR‑6.3: RUL countdown and maintenance advisory panel.\\n - FR‑6.4: Mission control panel to start/stop missions and inject faults.\\n7. Replay \& Reporting\\n - FR‑7.1: Re‑play historical mission data on demand.\\n - FR‑7.2: Generate a PDF/HTML mission report summarising health trends, detected faults and recommended actions.\\n\\n## 6. Non‑Functional Requirements\\n- Performance: End‑to‑end latency (telemetry ingest → twin update → UI) ≤ 200 ms.\\n- Scalability: System must handle at least 1 engine (≈ 10 Hz telemetry) with headroom for future multi‑engine extension.\\n- Reliability: Automatic reconnection of WebSocket clients; graceful degradation if ML models are missing (fallback defaults).\\n- Security: No external network calls; all data stays within the local sandbox.\\n- Usability: Dashboard must be navigable without domain knowledge; tool‑tips explain each metric.\\n- Maintainability: Code organised as a monorepo with clear backend/, frontend/, ml/, simulator/, docs/ directories.\\n\\n## 7.
