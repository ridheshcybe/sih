# SIH26054 Machine-Learning Pipeline Guide

This guide explains the complete machine-learning pipeline in this repository. It describes what the code
does, why each step exists, how the models are measured, and what the latest
results really mean.

The project uses **synthetic telemetry**: computer-generated engine sensor
readings made by a physics-inspired simulator. The results are useful for
learning and for a demonstration, but they are not evidence that the models
are safe for a real aircraft or engine.

---

## 1. System overview and intuition

### 1.1 What the pipeline does

The pipeline watches engine-like sensor readings and produces four different
answers:

1. **Anomaly detection:** Does this window look unusual compared with healthy
   operation?
2. **Fault classification:** If something is wrong, which fault is it?
3. **Degradation estimation:** How worn or unhealthy is the engine on a scale
   from 0 to 1?
4. **RUL prediction:** How many hours of useful operation may remain?

These are separate questions, so the system uses separate models. A model is
the learned mathematical rule that turns input numbers into a prediction.

### 1.2 The medical diagnostic-team analogy

Imagine a patient visiting a medical team:

| Machine-learning model | Medical-team analogy | Question answered |
|---|---|---|
| Anomaly model | A screening nurse | “Does anything look abnormal?” |
| Fault classifier | A specialist doctor | “Which specific disease is most likely?” |
| Degradation model | A health assessor | “How serious is the condition right now?” |
| RUL model | A prognosis specialist | “How much useful time may remain?” |

The models complement one another. A high anomaly score does not by itself
identify a fault. A fault label does not directly say how many hours remain.
Degradation is a condition estimate, while RUL means **Remaining Useful Life**:
the predicted time until the asset is no longer expected to operate normally.

### 1.3 Important project limitation

The simulator creates clean, labeled patterns. Real engines contain sensor
calibration errors, changing weather, maintenance history, unknown faults, and
operator behavior that may not appear in this data. The repository therefore
labels this as an educational and hackathon prototype, not a flight-certified
system.

## 2. Data and feature representation

### 2.1 Raw data

The dataset is generated by `python -m simulator.generate_dataset` and is
stored as:

- `data/train.csv`: 192,000 telemetry rows
- `data/val.csv`: 44,000 telemetry rows
- `data/test.csv`: 44,000 telemetry rows

The split is by **mission**, not by randomly scattering rows. This matters:
rows from one mission are related in time, so putting parts of one mission in
both training and testing would make the result look better than it really is.
The repository documentation describes 48 training/validation missions and
11 test missions in the generated report.

The simulator includes four operating profiles:

- `standard_isr`
- `high_altitude`
- `hot_weather`
- `aggressive`

The 12 sensor/control columns are:

| Column | Plain-English meaning |
|---|---|
| `rpm` | Engine rotations per minute |
| `cht` | Cylinder-head temperature |
| `egt` | Exhaust-gas temperature |
| `oil_pressure` | Lubrication-system pressure |
| `oil_temperature` | Oil temperature |
| `fuel_flow` | Fuel used per unit time |
| `vibration_rms` | Overall vibration strength |
| `battery_voltage` | Electrical-system voltage |
| `alternator_current` | Current produced by the alternator |
| `injection_timing` | Timing of fuel injection |
| `altitude` | Operating altitude |
| `ambient_temperature` | Outside temperature |

Labels are the correct answers used during supervised learning:

- `fault_label`: `none` or one of seven injected fault types
- `fault_severity`: fault strength from 0 to 1
- `degradation_level`: engine degradation from 0 to 1
- `rul_label`: remaining useful life in hours

The seven fault types are `misfire`, `injector_degradation`,
`lubrication_issue`, `overheating`, `sensor_drift`, `abnormal_vibration`, and
`battery_alternator_degradation`.

### 2.2 Why the code uses windows

One reading is often not enough. For example, one high temperature could be a
brief normal event, but ten readings that steadily rise are more suspicious.

`ml.feature_extractor.FeatureExtractor` uses a **window** of 10 consecutive
rows. With the simulator's timing, this represents roughly three seconds.
Windows start every two rows, called a **stride** of 2. A window never crosses a
`mission_id` boundary.

### 2.3 The 78 input features

There are 12 channels and six summary values per channel:

1. `last`: the newest reading in the window
2. `mean`: the average reading
3. `std`: standard deviation, measuring how much it fluctuates
4. `min`: smallest reading
5. `max`: largest reading
6. `slope`: the trend, such as steadily rising or falling

That gives `12 × 6 = 72` features.

The extractor adds six **physics residuals**:

> residual = observed value − expected healthy value

Residuals are computed for:

- `cht`
- `egt`
- `oil_pressure`
- `oil_temperature`
- `vibration_rms`
- `fuel_flow`

Therefore the final input has `72 + 6 = 78` dimensions.

The expected value comes from a healthy-model twin recorded by the simulator
when available. The fallback uses the engine model and the controls
`throttle`, `altitude`, and `ambient_temperature`. A residual near zero means
the observed value agrees with the healthy expectation; a large residual is a
possible fault signature.

Missing sensor values are linearly interpolated from nearby valid values. If a
whole sensor column is missing in a window, it is filled with zero. A real
deployment would need a carefully tested missing-data policy because zero may
not be physically meaningful.

### 2.4 Supporting modules

| Module | Responsibility |
|---|---|
| `simulator/__init__.py` | Defines sensor and label column names |
| `simulator/generate_dataset.py` | Builds and writes synthetic train/validation/test CSV files |
| `ml/feature_extractor.py` | Converts telemetry windows into 78-number vectors |
| `ml/data_utils.py` | Loads CSV files, builds features, encodes labels, saves metadata |
| `ml/train_anomaly.py` | Original Isolation Forest baseline |
| `ml/train_fault_classifier.py` | Original Random Forest fault baseline |
| `ml/train_degradation_rul.py` | Original Random Forest regression baselines |
| `ml/optimize_pipeline.py` | Bounded cross-validation optimization loop |
| `models/optimized/` | Selected serialized models and JSON metadata |
| `reports/` | Evaluation summaries and iteration logs |

## 3. Metrics and terminology guide

The target in this project is **0.98**, or 98%, for every required
classification metric. A metric is a numerical way to judge model quality.

### 3.1 Confusion-matrix vocabulary

For a binary “fault or no fault” decision:

- **True positive (TP):** The model says “fault” and a fault really exists.
- **True negative (TN):** The model says “healthy” and it really is healthy.
- **False positive (FP):** The model says “fault,” but the machine is healthy.
  This is a false alarm.
- **False negative (FN):** The model says “healthy,” but a fault exists. This
  is a missed fault.

### 3.2 Accuracy

**Accuracy** is the fraction of all predictions that are correct:

`accuracy = (TP + TN) / (TP + TN + FP + FN)`

If a model makes 98 correct predictions out of 100, its accuracy is 0.98.
Accuracy can be misleading when classes are imbalanced. If 95 of 100 machines
are healthy, a lazy model that always says “healthy” gets 95% accuracy while
missing every fault.

### 3.3 Precision

**Precision** asks: “When the model raises an alarm, how often is it right?”

`precision = TP / (TP + FP)`

Of 20 alarms, if 19 are real faults and one is false, precision is 19/20 =
0.95. High precision reduces unnecessary inspections and repairs. In the
medical analogy, it means that a positive test is usually a real disease.

### 3.4 Recall

**Recall**, also called sensitivity, asks: “Of all real faults, how many did
the model find?”

`recall = TP / (TP + FN)`

If 100 faults occur and the model finds 98, recall is 0.98. High recall is
important when missing a dangerous fault is worse than creating a false alarm.
In the medical analogy, high recall means the screening test misses very few
patients who truly have the disease.

### 3.5 F1-score

**F1-score** combines precision and recall into one balanced score:

`F1 = 2 × precision × recall / (precision + recall)`

It is high only when both precision and recall are high. A model cannot get a
strong F1 by finding every fault while producing many false alarms, or by
being very precise while missing most faults.

The pipeline uses **macro averages** for multiclass precision, recall, and F1.
Macro averaging calculates each class's score separately and then gives every
class equal importance. This prevents the large healthy `none` class from
hiding weak performance on a smaller fault class.

### 3.6 ROC-AUC

**ROC-AUC** means “area under the Receiver Operating Characteristic curve.”
It measures how well a model ranks real positives above negatives over many
possible alarm thresholds:

- 1.0 means perfect ranking.
- 0.5 means random ranking.
- Below 0.5 is worse than random.

ROC-AUC can be excellent even when one chosen threshold gives weak recall.
That is exactly why the report shows anomaly ROC-AUC near 1.0 but still checks
the chosen-threshold precision and recall.

For the eight-class fault model, the code uses one-versus-rest multiclass
ROC-AUC and averages the class results.

### 3.7 R²

**R²**, or the coefficient of determination, measures how much of the
variation in a numeric target is explained by predictions:

`R² = 1 − (prediction error squared / error from always using the average)`

- 1.0 means perfect predictions.
- 0 means no better than always predicting the training average.
- A negative value means worse than that simple average baseline.

For degradation and RUL, R² is the main 0.98 target.

### 3.8 MAE

**MAE**, mean absolute error, is the average size of the prediction mistake:

`MAE = average(|actual − predicted|)`

If actual RUL values are 100, 80, and 60 hours and predictions are 95, 84,
and 63, the errors are 5, 4, and 3 hours, so MAE is 4 hours. Unlike R², MAE
has the same unit as the target and is easy to interpret. Lower is better.
MAE is reported for regression but is not the 0.98 pass/fail metric in this
pipeline.

## 4. Model-by-model deep dive

### 4.1 Binary anomaly detection

The optimizer turns the fault label into a binary target:

- `0`: `none`, healthy
- `1`: any of the seven faults

The optimization candidate that won was a **balanced Random Forest**.

A **decision tree** is a sequence of questions such as:

1. Is vibration above a limit?
2. Is the oil-pressure residual negative?
3. Is the temperature slope positive?

The final leaf gives a prediction. A **Random Forest** grows many trees using
different samples and feature choices, then combines their votes. This is like
asking many slightly different inspectors and using the majority decision.

The anomaly candidate's important hyperparameters are:

| Hyperparameter | Value | Meaning |
|---|---:|---|
| `n_estimators` | 100 | Number of trees |
| `min_samples_leaf` | 1 | Smallest number of samples allowed in a leaf |
| `max_features` | `sqrt` | Each split considers roughly the square root of all features |
| `class_weight` | `balanced_subsample` | Gives extra influence to underrepresented classes in each tree sample |
| `n_jobs` | -1 | Uses all available CPU cores |
| `random_state` | 0 | Makes the experiment repeatable |

The optimizer also searches a probability threshold from 0.05 to 0.95. The
default threshold is often 0.50, but a different threshold can trade false
alarms against missed faults. The selected threshold is stored in anomaly
metadata.

### 4.2 Multiclass fault classification

This model predicts one of eight labels:

`abnormal_vibration`, `battery_alternator_degradation`,
`injector_degradation`, `lubrication_issue`, `misfire`, `none`,
`overheating`, and `sensor_drift`.

The selected final model is a **balanced Extra Trees classifier**.

**Extra Trees**, short for Extremely Randomized Trees, is related to Random
Forest. Both use many decision trees. Extra Trees adds more randomness when
choosing split points. More varied trees can reduce the chance that the whole
ensemble memorizes one narrow pattern.

Its important settings are:

| Hyperparameter | Value | Meaning |
|---|---:|---|
| `n_estimators` | 120 | Number of randomized trees |
| `min_samples_leaf` | 1 | A leaf may contain one training example |
| `max_features` | 1.0 | Each split can use all input features |
| `class_weight` | `balanced` | Automatically gives smaller classes more weight |
| `n_jobs` | -1 | Uses all CPU cores |
| `random_state` | 0 | Repeatable randomness |

The first iteration used a balanced Random Forest. It produced a strong
cross-validation result but weaker validation macro precision, recall, and F1.
The second iteration switched to balanced Extra Trees and passed every
validation target.

### 4.3 Degradation estimation

This is a regression task: instead of selecting a named class, the model
predicts a continuous number from 0 to 1.

The selected candidate is an **Extra Trees Regressor**. A regressor predicts a
number rather than a category. Each tree makes a numeric estimate and the
ensemble averages the tree estimates.

Settings:

| Hyperparameter | Value |
|---|---:|
| `n_estimators` | 120 |
| `min_samples_leaf` | 1 |
| `max_features` | 1.0 |
| `n_jobs` | -1 |
| `random_state` | 0 |

The main target is R² ≥ 0.98. MAE is also recorded so a reader can understand
the typical absolute error.

### 4.4 RUL prediction

RUL means **Remaining Useful Life**, measured here in hours. The RUL model
uses the same 78 features as degradation. In the original baseline trainer,
the degradation label is appended as an additional input, producing a
79-dimensional RUL input. The optimization script evaluates the direct
78-feature RUL candidate.

The selected optimizer candidate is also an Extra Trees Regressor. The
intuition is that degradation patterns and sensor trends can be split into
regions, then the trees average the expected remaining hours in the matching
regions.

RUL is a difficult operational prediction: a small sensor error can translate
into several hours of error. Therefore both R² and MAE should be inspected.

### 5.2 Cross-validation and validation results by iteration

**Cross-validation (CV)** repeatedly divides the training portion into folds.
For three-fold CV, the model trains on two parts and scores on the third,
rotating until every part has been used for scoring. This estimates how stable
the model is across different samples.

Validation is a separate mission-level split used to choose the best
candidate. It is not the final test.

### 5.4 Why each result happened

**Anomaly succeeded on ranking but is borderline on recall.** The anomaly
classifier separates healthy and faulty windows very well overall, shown by
ROC-AUC 0.9998. However, a chosen probability threshold can still miss a few
faults. The validation threshold looked excellent but transferred slightly
less well to unseen test missions. This is a threshold/generalization issue,
not evidence that the features contain no useful signal.

**Fault classification improved strongly after Extra Trees.** The first
balanced Random Forest had a validation macro recall of 0.9517, roughly a 5%
gap from the requested 0.98. Possible causes include overlapping signatures
between faults, mission-specific patterns, and unequal class representation.
Balanced class weights helped, but the Extra Trees model's additional split
randomness and full-feature consideration produced a much better boundary.
The final held-out fault metrics all exceed 0.999.

**Degradation and RUL succeeded because the simulator is structured.** The
physics-inspired simulator creates consistent relationships among residuals,
severity, degradation, and RUL. Tree ensembles can learn those repeated
relationships, so R² remains above 0.98 on held-out missions. This result is
excellent for the synthetic benchmark but should not be assumed for real
telemetry.

## 6. Complete workflow and architecture

### Step 1: Generate or load data

`ml.data_utils.load_splits()` reads `train.csv`, `val.csv`, and `test.csv`.
If a file is missing, the code raises an explicit error telling the user to
generate the dataset.

### Step 2: Build windows

`build_window_dataset()` groups rows by mission, creates 10-row windows with
stride 2, and never allows a window to combine two missions.

For every window it returns:

`X, fault labels, degradation values, RUL values, feature names`

### Step 3: Encode classes

The eight text fault labels are sorted and mapped to integer IDs. For anomaly
detection, all labels except `none` become class 1.

### Step 4: Prepare CV samples

The optimizer can limit CV to `--cv-sample` rows. Classification samples are
drawn with an approximately equal per-class allocation before any remaining
slots are filled. Regression samples are randomly selected. This reduces
runtime; final model fitting still uses all training windows.

### Step 5: Try model candidates

Classification candidates cycle through:

1. Balanced Random Forest
2. Balanced Extra Trees
3. Extra Trees feature selection plus Extra Trees
4. Histogram Gradient Boosting
5. Scaled Logistic Regression with model-based feature selection

Regression candidates cycle through:

1. Extra Trees Regressor
2. Random Forest Regressor
3. Histogram Gradient Boosting Regressor

### Step 6: Cross-validate

`StratifiedKFold` is used for classification. **Stratified** means each fold
keeps a similar class mix, so a small fault class is not accidentally absent
from a fold. The default is three folds, shuffled with `random_state=0`.

`cross_validate()` calculates:

- Classification: accuracy, macro precision, macro recall, macro F1, and
  ROC-AUC
- Regression: R²

### Step 7: Fit on all training data and score validation

Each candidate is then trained on all `X_train` data and measured on
`X_val`. The weakest required metric is used as the candidate score:

`candidate score = minimum(required metric values)`

This prevents a model from winning only because it has excellent accuracy
while having poor recall.

### Step 8: Tune the binary anomaly threshold

For anomaly detection only, the code tests 91 thresholds from 0.05 to 0.95.
For every threshold it calculates accuracy, precision, recall, and F1. It
chooses the threshold with the highest weakest metric. ROC-AUC is kept
threshold-independent.

### Step 9: Stop or continue

The loop stops early when all tasks meet every required validation metric.
Otherwise it continues until the requested maximum, which cannot exceed 15.
This cap prevents an endless search.

### Step 10: Fit selected models and evaluate test once

The selected model for each task is refit using the complete training split,
then evaluated on the untouched test split. Models are saved with `joblib`.
Each JSON metadata file stores:

- Task name
- Model name
- Target threshold
- Class list where relevant
- Feature names
- Serializable hyperparameters
- Selected validation metrics
- Final test metrics
- Anomaly decision threshold, when applicable

### Step 11: Write reports

The optimizer creates a timestamped report in `reports/` with:

- Target threshold
- Number of iterations
- Runtime
- Final test metrics
- Every iteration's candidate, CV metrics, and validation metrics
- Artifact location

## 7. How to run and load the result

Use the project environment that contains the installed scikit-learn and
joblib packages:

```bash
/home/coder/.venv/bin/python -m ml.optimize_pipeline \
  --max-iterations 15 \
  --cv-folds 3 \
  --cv-sample 4000
```

The defaults are `max-iterations=15`, `cv-folds=3`, and `cv-sample=20000`.
The documented run used `cv-sample=4000` to complete in a practical amount of
time. A larger CV sample may give a more stable search but takes longer.

Artifacts are written to `models/optimized/`:

- `anomaly_model.joblib`
- `fault_model.joblib`
- `degradation_model.joblib`
- `rul_model.joblib`
- `anomaly_meta.json`
- `fault_meta.json`
- `degradation_meta.json`
- `rul_meta.json`

Example loading code:

```python
import joblib

fault_model = joblib.load("models/optimized/fault_model.joblib")
fault_predictions = fault_model.predict(X_new)
fault_probabilities = fault_model.predict_proba(X_new)
```

The new input `X_new` must be created by the same 78-feature extractor in the
same order. A model file without matching feature construction is unsafe to
use because the model would interpret each number as the wrong sensor
quantity.

## 8. Actionable improvement plan

The final fault classifier already meets the 98% target on the held-out test
set. The first iteration nevertheless shows how a roughly 3–5% validation gap
can appear, and anomaly recall remains slightly below the strict target.

### 8.1 Improve fault robustness

1. **Inspect the confusion matrix.** Count which faults are confused with
   which others. This is more useful than changing models blindly.
2. **Use class weights.** The optimizer already uses `balanced` or
   `balanced_subsample`, which makes mistakes on small classes more costly.
3. **Try SMOTE carefully.** SMOTE, Synthetic Minority Over-sampling Technique,
   creates new minority-class points by interpolating between existing points.
   It can help a rare fault class, but it must run inside each CV training fold,
   never before the split. Otherwise synthetic information can leak into the
   validation fold.
4. **Try gradient boosting.** XGBoost, LightGBM, or CatBoost build trees in
   stages, where later trees focus on earlier mistakes. They may model subtle
   differences between `misfire`, `abnormal_vibration`, and `sensor_drift`.
   They require dependency review and careful parameter control.
5. **Add class-specific tuning.** One class may need a different probability
   threshold from another. Evaluate macro recall and macro F1 after tuning,
   not just overall accuracy.
6. **Collect more mission diversity.** Since the CV-to-validation difference
   was large in iteration 1, new mission profiles and fault severities may
   improve generalization more than another model family.

### 8.2 Improve anomaly recall

1. Evaluate thresholds on multiple validation missions rather than one
   threshold selected from a single validation result.
2. Select a threshold with an explicit safety constraint, such as recall at
   least 0.99, then measure the resulting precision and false-alarm rate.
3. Calibrate probabilities. A probability is calibrated when predictions near
   0.8 are correct about 80% of the time; tree probabilities are not always
   calibrated automatically.
4. Combine the learned score with the physics-residual score and test the
   combination on separate missions.
5. Add real or hardware-in-the-loop data before claiming operational
   reliability.

### 8.3 Correct experimental safeguards

Every future experiment should keep these rules:

- Split by mission or time period, not by nearby rows.
- Fit scaling, feature selection, and SMOTE only inside training folds.
- Never choose a model using the final test labels.
- Report macro metrics when classes are imbalanced.
- Save the exact feature order, hyperparameters, random seed, and data
  version next to the model.
- Repeat the final evaluation on more than one held-out mission set when
  possible.

## 9. Final interpretation

The optimization loop is technically successful as an experiment: it improves
fault classification dramatically, keeps degradation and RUL above the target,
and finds an anomaly score with excellent ranking. However, the strict
“every metric ≥ 0.98” requirement is not fully satisfied because held-out
anomaly recall is slightly below 0.98. The correct scientific conclusion is
therefore:

> The final optimized models are strong on this synthetic benchmark, but the
> complete 98% requirement has not been proven for every held-out metric.

That honest conclusion is more valuable than reporting a rounded 0.9800 as a
guaranteed pass.
